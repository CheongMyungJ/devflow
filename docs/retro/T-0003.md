## 세 역할 분리는 코드 변경 Task 에서도 성립하는가 (이 Task 의 시험)

**성립했다.** 근거:
- Worker 는 패킷(경로 목록)만 받고 스키마 6개·테스트 23개(step-001), 스크립트 재작성·테스트 36개(step-002), 역할 프롬프트 5개(step-003)를 끝까지 혼자 했다. 도중에 사람이나 Orchestrator 에게 물은 적이 없다. 모든 실행이 작업 노트에 설계 선택·버린 대안·"확인하지 못한 것" 을 남겼다.
- 재작업의 이어받기가 코드 Step 에서도 성립했다(R-004: 4분, "이어받는 데 부족한 것은 이 정도" 가 한 건). 끊긴 실행의 이어받기도 성립했다(R-013 이 R-012 의 잔여물을 받아 README 문장은 그대로, reviewer.md 문장은 결함이 있어 고쳐 썼다 — 그대로 주워 쓰지 않고 판단했다).
- 여러 Step 에 걸친 Planner 의 이어받기가 성립했다(네 번의 Planner 가 모두 새 세션. 아래 "Ledger").
- Reviewer 가 실제 결함을 실측으로 잡았다: 생성 타입의 Step.inputs 에 어떤 문자열도 대입되지 않는다(R-003, tsc 로 확인 — typecheck·test 는 통과하고 있었다), planner.md 만 보고 쓴 next_step 이 거부된다(R-011). 둘 다 Worker 의 "확인하지 못한 것" 을 공격하다 나왔다 — T-0001, T-0002 와 같은 패턴이 세 번째다.
- 역할 사이의 견제가 실제로 일했다: Intake 가 놓친 것("이 Task 자신의 기록도 옛 형식이라 merge 뒤에 새 스키마로 검사된다")을 Planner(R-001)가 찾았고, Worker 가 추론으로 넘어간 것("검증 동작은 그대로다")을 Reviewer(R-005)가 44개 값으로 확인했고, Orchestrator 가 "확인은 다음 실행의 몫" 으로 남긴 것(decision 스키마가 step 의 안쪽을 검사하는가)을 Worker(R-013)가 확인했다.

한계: Worker 와 Reviewer 가 같은 모델이다(다른 모델로 돌리는 이점은 여전히 시험되지 않았다). 실행 중 개입, `ask_human`, 질문, 요구사항 추가, 사람의 직접 수정의 경로는 이번에도 시험되지 않았다 — 서브에이전트를 띄우고 끝날 때까지 기다리는 수동 운영에서는 실행 중 개입을 구조적으로 시험할 수 없다.

## Planner Step 제안을 사람이 고친 것
- 없음. D-001~D-003 을 모두 그대로 확정했다(`human_edit: false` 셋). T-0002 까지 합치면 네 번 연속이다.
- Planner 는 D-002 부터 "승인된 기록에 없던 것을 내가 새로 정했다" 를 스스로 분리해 올렸다(D-002 의 설계 셋, D-003 의 넷). 사람이 실제로 본 것은 그 부분이었다. "Step 제안 확인을 기본이 아니라 조건부로" 의 근거가 된다(backlog 의 "사람 리뷰가 들어가는 자리").
- Planner 의 분할 판단은 좋았다: D-001 의 예상(record-gate + 프롬프트 한 Step)을 D-002 가 뒤집어 둘로 나눴고(검증의 성격이 다르다, 스키마에 고칠 곳이 드러난다면 프롬프트를 쓰기 전이 싸다), 실제로 step-003 에서 재작업이 났을 때 record-gate 는 묶이지 않았다.

## 재작업
- step-001 v1→v2: **Step 정의 부실.** 스키마에 pattern 을 더한 결과 생성 타입이 쓸 수 없게 되었는데, verify 의 어느 질문도 "생성 타입에 실제로 대입되는가" 를 묻지 않았다. Worker 는 "확인하지 못한 것" 에 적었고 Reviewer 가 실측으로 확정(B 등급), 사람이 수정을 요청했다(F-001). 스키마를 고치는 Step 에는 "생성 타입을 실제로 써 보는 검사" 가 verify 에 있어야 한다.
- step-003 v1→v2: **Step 정의 부실 + Worker 의 선택.** planner.md 의 출력 절이 next_step 의 안쪽 모양을 말하지 않았고(Step 은 "틀리기 쉬운 것을 말하고 스키마를 가리킨다" 고만 했다), Worker 가 부딪힘을 풀려고 고른 문장("그 디렉터리와 출력 파일 말고는 아무것도 만들지 않는다")이 Workspace 에서의 실행을 막았다. 둘 다 "프롬프트만 읽고 그대로 한 세션이 막히는" 문제라 사람이 수정을 요청했다(F-007).
- Gate fail 은 없었다(G-001~G-005 모두 pass). 재작업 둘은 모두 "Reviewer 는 pass, 사람은 수정 요청" 이다. Gate 오판이라기보다 B 등급("승인해도 되지만 후속에서")의 경계 문제다 — Reviewer 는 done_when 이 충족되면 A 로 올리지 않았고(지침대로다), "다음 Task 가 막히는가" 는 사람이 판단했다. step-002 에서는 같은 종류의 B(gate id 검사)를 사람이 승인했다 — 기준은 "그대로 두면 다음 Task 에서 반드시 터지는가" 였다.
- 실패한 실행 R-012: 사용량 한도(HTTP 429)로 끊겼다. 변경은 거의 끝나 있었으나 commit 도 작업 노트도 없었다. **작업 노트를 끝에 몰아 쓰는 방식은 끊김에 약하다.** R-013 부터 "commit 직후에 노트를 먼저" 를 패킷에 넣었다.

## 실행 중 개입
- 없음. 사람의 말은 Step 확정 3회, 검토 5회(승인 3, 수정 요청 2), Task 수준의 방향 지시 1회(F-004 — 범위 밖에서 발견된 문제를 "다뤄도 된다, 지시는 아니다"), done 확정으로만 들어갔다.

## Ledger (기억 없는 Planner 가 목표를 이어가는 근거) — 세 번의 실측
- R-006(step-001 뒤): "상세가 Ledger 가 아니라 Gate 와 작업 노트의 특정 절에 있었고 Ledger 는 그 절이 있다는 것을 말하지 않았다." 274초, 13.3만 토큰.
- → Ledger 쓰는 방식을 바꿨다: 요약 + **뒤의 Step 이 알아야 할 것** + **상세가 있는 곳**(어느 Artifact 의 어느 절, 어느 Gate).
- R-009(step-002 뒤): "다음 행동이 무엇인가는 Ledger 만으로 정해졌다. 헤매지 않았다." 다른 파일은 Step 정의를 쓰려고 읽었고 "Ledger 가 담을 일은 아니다".
- R-015(step-003 뒤): "done 이냐 Step 이냐의 판단은 Ledger 와 Task 정의만으로 섰다." 168초 — 네 번 중 가장 짧았다.
- 손으로 쓰는 Ledger 의 결함도 드러났다: "진행 중" 절에 옛 줄이 남아 Planner 가 한 번 더 읽었다(R-009), "후속 Task 후보" 절이 끝까지 비어 있었고 후보는 각 Step 요약에 흩어져 있었다(R-015 가 모았다). "MVP 에서 Ledger 는 누가 어떤 규칙으로 쓰는가"(backlog)의 판단 재료: 기계적 조립(Worker 의 summary + Gate 의 B 등급)만으로는 "뒤의 Step 이 알아야 할 것" 이 안 나온다 — 그것은 누군가의 판단이다.

## 반복 패턴 (Skill 후보)
- **스키마 → 그것을 받는 코드 → 그것을 말하는 문서(프롬프트)** 의 3단 구성. T-0001 의 "설계 → 구현 → 호출자·문서 정합" 과 같은 꼴이다. 두 번째 관찰.
- **"문서 하나만 보고 해 본다" 실험**: 프롬프트·문서가 받는 쪽(스키마, 스크립트)과 맞는지를 읽어서가 아니라, 그것만 읽은 눈으로 출력을 써서 실제로 넣어 보는 것. D-003 의 Planner 가 검증에 넣었고, Worker(R-012, R-013)는 스스로 하위 세션을 띄워 "그것만 읽은 눈" 을 만들었다. 깨끗하게 하려면 **읽는 순서를 패킷이 정해야 한다**(R-011 은 작업 노트에 예시 전문이 있어 조건이 깨졌다고 보고했고, R-014 는 "다른 파일을 열기 전에 먼저" 로 성립했다). 한계: 이 실행 환경은 Workspace 의 AGENTS.md 를 세션에 자동으로 넣는다 — Runner 가 역할 세션에 무엇이 들어가는지 통제해야 한다.
- 옛 기록과의 공존: "배열 전체가 옛 형식일 때만 옛 형식으로 받는다"(섞인 배열 거부) + 옛 형식의 허용을 Task ID 에 묶지 않는다 + validate-data 에 예외를 두지 않는다. 스키마를 바꾸는 다음 Task 에서 다시 쓸 것이다.
- Orchestrator 의 반복 동작(스크립트 후보): Run 기록의 submitted → completed, Artifact meta 작성, 승인 Feedback 둘 + 이벤트 여섯, deterministic 재실행과 `G-NNN.deterministic.md`. 이 Task 에서 Run 14개·이벤트 104개를 손으로(PowerShell 조각으로) 썼다. backlog 3번(Store 에 나머지 엔티티)이 이것을 없앤다.

## Context 부족 / 과잉
역할 세션 15회가 packet_gaps 를 보고했다. 같은 것을 여러 세션이 독립적으로 지적한 것:
- **verify 의 명령이 대상 repo 밖의 checkout 을 인자로 받는다** (R-001, R-002, R-004, R-006, R-007, R-009, R-010, R-013): Planner 는 run 을 서술로 쓸 수밖에 없고, Orchestrator 가 패킷에 실제 명령을 채우고, Worker 는 그 명령을 작업 노트에 옮겨 적지 못한다(로컬 경로). T-0002 와 같은 문제 — backlog 에 그대로 있다.
- **"구조를 바꾸는 결정 → ADR" 의 기준이 없다** (R-001, R-002). Worker 는 ADR-0012 를 썼고 Reviewer 는 받아들였다.
- **Step 정의 안의 부딪힘**: "테스트에 로컬 경로를 쓰지 않는다" ↔ "로컬 경로가 거부되는 테스트"(R-003), "추적 파일을 고치지 않는다" ↔ "실행해서 확인한다"(mutation 확인 — R-003, R-005), Task 의 "docs/ 는 범위 밖" ↔ "구조를 바꾸면 architecture.md 갱신"(R-009).
- **재작업 중 범위 밖에서 같은 종류의 문제를 찾았을 때** 고쳐도 되는지 어디에도 없다(R-004). Worker 는 고치지 않고 적었다 — 옳은 기본값이었다. worker.md 에 넣을 만하다.
- 패킷의 틀에 빠져 있던 것(Orchestrator 가 Task 도중에 더했고 절차 문서에 반영했다): Worker 의 summary 를 적을 자리(R-002), artifact 참조에서 본문을 찾는 법(R-006), 다른 repo 의 기준 상태를 작업 중인 checkout 이 아니라 고정된 checkout 으로(R-001), 재작업의 Reviewer 에게 "앞 버전의 노트와 합쳐 판정"(R-005), 임시 디렉터리에서 복사본을 고쳐 봐도 된다(R-005), 역할 프롬프트를 고치는 Task 에서 "따를 지침과 고치는 대상의 구별"(R-010 부터).
- 과잉은 보고되지 않았다. 다만 Step 정의가 길다(step-003 은 115줄 — 완료 조건 13개, 검토 질문 9개). 사람이 Step 제안을 실제로 평가하기 어려운 길이다.
- 기준 문서들 사이의 어긋남이 드러났다(역할 세션이 기준을 직접 읽었기 때문에): Reviewer 가 checks 에 deterministic 항목을 적는가(네 곳이 다르게 말한다), roles/README.md 는 출력을 JSON 이라 하는데 0단계의 Planner 출력은 YAML, architecture.md 의 "읽기 전용 실행 뒤 worktree 변경 → 무효" 와 git 이 무시하는 생성물.

## 기록의 정확성
- 시각은 모두 얻어서 적었다. `run.completed` 의 `at` 은 Orchestrator 가 기록한 시각이고, 실제 종료 시각은 Run 의 `ended_at`(Worker 의 자기 기록 또는 출력 파일의 마지막 쓰기 시각)에 적었다. R-012 의 끊긴 시각은 알 수 없다.
- 스키마 검증이 Orchestrator 의 실수를 한 번 막았다(submitted 상태의 Run 에 `output_attempts: 0`). PowerShell 조각의 오류로 Ledger 갱신이 한 번 실패했다(commit 전, 변경 없음 — Edit 로 다시 했다).
- Orchestrator 가 "띄우기 직전에 보고하겠다" 고 하고 Planner 를 바로 띄운 일이 한 번 있다(되돌리기 쉬운 일이라 판단했고 그렇게 보고했다).
- 이 Task 자신의 기록(옛 형식)이 merge 뒤 새 스키마로 통과함을 main 에서 확인했다(345 checked, 0 failed — task.done 전).
- Task 가 진행되는 동안 repo devflow 의 main 은 c01a300 에서 움직이지 않았다. T-0002 의 "기준 SHA 가 흔들렸다" 는 되풀이되지 않았다.
- artifact meta(`vN.meta.yaml`)는 validate-data 의 검사 대상이 아니다 — 손으로 쓴 meta 12개는 스키마로 검사된 적이 없다.

- packet_gaps(15회의 실행, 중복을 빼고 주제 약 12개) → 절차 문서에 반영 6, backlog 3(verify 의 명령, ADR 의 기준, 범위 밖 발견의 처리), 나머지는 그 실행에 한정된 것.
- 옮기면서 필요했던 판단: (a) 이미 닫힌 것인가 — Gate 는 뒤의 Step 이 닫았는지 모른다, 사람이 Ledger 와 뒤의 Gate 를 대조해야 했다 (b) 같은 지적의 되풀이인가 — G-004 의 B 가 G-005 에 "그대로" 로 다시 나온다 (c) 어디로 가는가 — 절차 문서 / 다음 Task 의 범위 / 설계 결정(정할 것) / 관찰. (d) Ledger 의 "후속 Task 후보" 절은 끝까지 비어 있었다 — 손으로는 "나올 때마다 적는다" 가 지켜지지 않았다. 기계가 모을 수 있는 것은 (a)(b) 의 재료(어느 Gate 의 어느 지적이 뒤의 어느 Feedback·Gate 에서 언급되었는가)까지이고 (c) 는 판단이다.
