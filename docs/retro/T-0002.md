Worker 는 작업 노트에 이 문제를 스스로 적었고, Reviewer(G-001)가 B 등급 risk 로 올렸고, 사람이 수정을 요청했다(F-001). 기준 문서(store.md 2.1)의 표현은 "git 에 넣지 않음" 이었다 — Planner 가 기준 문서의 용어 대신 자기 말로 완료 조건을 썼다.
- Gate fail 은 없었다(G-001, G-002 모두 pass). Gate 오판도 없었다.

## 반복 패턴 (Skill 후보)
- 역할 세션에 주는 패킷의 틀이 세 역할 모두 같았다: 역할 지침 경로 / Step·Task 정의 경로 / inputs 의 참조 → 로컬 위치 매핑 / (재작업이면) 이전 버전·작업 노트·Feedback·Gate / 출력 파일 경로와 형식 / 금지 / 마지막 응답에 담을 것. 1단계의 "Context 패킷 조립" 이 만들 것이 바로 이것이다. 지금은 대화 세션이 매번 손으로 썼다.
- Orchestrator 의 반복 동작을 스크립트로 옮겼다: `propose-step`(Decision → step.yaml), `record-gate`(Reviewer 출력 → Gate). Run·Artifact meta·Feedback 의 기록과 상태 전이는 아직 손으로 한다 — backlog 3번(Store 에 나머지 엔티티)이 끝나면 commands 로 바뀐다.
- Reviewer 에게 준 두 지시("실행해서 확인", "'확인하지 못한 것' 을 먼저 공격")는 이번에도 효과가 있었다: R-005 는 Worker 가 v2 에서 생략한 실제 파일 ignore 확인과, 두 Worker 가 모두 하지 못한 "기준 SHA 의 스크립트로 validate-data" 를 직접 했다.

## Context 부족 / 과잉
**roadmap 의 위험 2("Context 패킷만으로 새 세션의 Worker 가 충분히 작업할 수 있는가")를 처음 측정했다. 이 크기의 문서 Task 에서는 성립했다.** 재작업도 이전 세션의 작업 노트만으로 이어받았다(R-004: "부족한 것이 없다고 해도 될 정도" — R-002 의 노트가 문제의 원인과 문장의 출처를 적어 두었기 때문). 코드 구현 Step 과 여러 Step 에 걸친 Task 는 아직 시험하지 못했다.

역할 세션들이 보고한 부족(같은 것을 여러 세션이 독립적으로 지적했다):
- **verify 의 명령이 대상 repo 밖에 있다** (R-001, R-002, R-003, R-004, R-006): validate-data 는 repo devflow 의 스크립트인데 상태 기록에 로컬 경로를 쓸 수 없어 `run` 이 서술이 되었다. 어느 SHA 의 스크립트가 기준인지도 없다. Orchestrator 가 운영 스크립트를 main 에 계속 commit 해서 clone 의 HEAD 가 실행마다 달랐다(1f5aabd → 75ca018).
- **Feedback 이 완료 조건을 바꿨는데 반영할 자리가 없다** (R-004, R-005, R-006): F-001 뒤에도 step.yaml 의 done_when 과 task.yaml 의 AC3 에는 옛 문구가 남았다. Orchestrator 가 Reviewer 패킷에 "F-001 이 우선한다" 고 써서 넘겼다.
- **AC 의 기준 시점** (R-001, R-006): AC5 의 "validate-data 통과" 가 worktree 기준인지 merge 뒤 main 기준인지. main 기준이면 Planner 는 done 을 낼 수 없다. Intake 의 부족이다.
- `.devflow.yaml` 없는 repo 에서 직접 명령이 허용되는가, 다른 repo 를 `inputs` 에 넣는 문법과 그 clone 의 위치를 받는 방법, 작업 노트의 위치와 형식(R-001). projects.yaml 의 스키마가 없다(R-003). Planner 가 읽기 전용 명령을 실행해도 되는가, completion 의 참조 형식(R-006). README 예시 ID 의 규칙, 작업 트리의 줄바꿈 설정(R-002, R-004).
- 과잉은 보고되지 않았다. 패킷은 경로 목록이었고 각 세션이 필요한 것만 읽었다.
- R-001 의 부족 보고는 최종 응답에만 있어 파일로 남지 않았다(Ledger 에 요지만 옮겼다). R-004 부터 출력 파일의 `packet_gaps` 로 받았다.

## 기록의 정확성
- 시각은 모두 얻어서 적었다. 다만 `run.completed` 의 `at` 은 "Orchestrator 가 기록한 시각" 이고 세션이 실제로 끝난 시각이 아니다 — R-002 는 12:21:50Z 에 끝났는데 Orchestrator 세션이 사용량 한도로 멈춰 13:42Z 에 기록되었다(이벤트의 note 에 남겼다). 백그라운드 세션의 종료 시각을 Orchestrator 가 알 방법이 지금은 Worker 의 자기 기록뿐이다.
- 스키마 검증이 Orchestrator 의 실수를 두 번 막았다: Planner 의 출력 파일(R-001.output.yaml)을 Run 기록으로 오인한 검사, 승인 Feedback 의 스키마에 없는 필드(`gate_id`). 둘 다 commit 전에 잡혔다.
- Orchestrator 가 Reviewer 패킷에 쓴 "store.md 1절" 은 0절이 맞았다(R-005 가 지적). 패킷을 손으로 쓰는 한 이런 오류는 계속 난다.
- Task 가 미등록 repo 를 대상으로 발행되었다(등록이 이 Task 의 AC5 였다). 발행 시 `target.repo` 를 등록부와 대조하는 검사가 없다.
- 기록 repo 와 대상 repo 가 같아 Task 가 진행되는 동안 base branch(main)가 계속 앞서갔다. 작업 파일과 기록 파일이 겹치지 않아 merge 충돌은 없었다. 1단계의 "base branch 이동 감지" 는 이런 경우를 정상으로 다뤄야 한다.
