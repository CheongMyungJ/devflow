# T-0001: State Store 인터페이스 + 파일 구현체 + Task 생성·조회

- 유형 / 대상 repo: feature / devflow
- Step 수 / 재작업 횟수 / 소요: 3 / 4 (step-001 2회, step-002 1회, step-003 1회) / 약 2시간 (`devflow-data` 의 commit 시각 기준 — 2026-09-18 19:02 Task 생성 ~ 20:56 done, KST). 이벤트의 `at` 으로는 계산할 수 없다(아래 "기록의 정확성").
- 결과: done (D-004, AC1~AC7 충족. main 에 직접 merge)
- 수행 주체: Intake·Planner·Worker 는 하나의 AI 대화 세션이 겸했고 Reviewer 만 매번 새 독립 세션이었다. 마무리(D-004, merge, 이 회고)는 Ledger 와 events.jsonl 로 상태를 복원한 두 번째 대화 세션이 했다. 이 회고는 그 세션이 기록만 보고 썼으므로, 기록에 남지 않은 것(사람이 대화 중에 한 말)은 빠져 있을 수 있다.

## Planner Step 제안을 사람이 고친 것
- 기록 없음. D-001~D-003 어디에도 `human_edit` 가 없다. 고치지 않은 것인지 적지 않은 것인지는 기록으로 구별할 수 없다. Planner 를 대화 세션이 겸했으므로 제안 전에 대화로 조율되었을 가능성이 있고, 그렇다면 roadmap 의 위험 1("Planner 가 검증 가능한 크기로 Step 을 자르는가")은 이 Task 로 측정되지 않았다.

## 재작업
- step-001 v1→v2: Step 정의 부실 + Worker 실수. Gate G-001 은 pass 였으나 설계 결함 3건(lock 없는 reader 의 경합, commit 시점 이후의 오류, stale lock 회수 경합)을 지적했고 사람이 수정 요청(F-001). 동시성 설계인데 Step 의 검증에 "전제를 실험으로 확인한다" 가 없었다.
- step-001 v2→v3: Worker 실수(방향). v2 가 결함을 메커니즘 추가로 막으려다 새 결함을 만들었다. 사람이 "더하지 말고 줄여라" 로 방향을 바꿨다(F-002) — 시간 기준 lock 회수를 없애는 단순화. 설계 검토 3회로 못 잡은 mtime 전제의 불성립을 실측 한 번(R-005 probe)이 잡았다.
- step-002 v1→v2: Worker 실수. Gate G-004 fail — Reviewer 가 실측으로 lock.ts 의 버그 3건 확인(획득 루프가 멈춤, 원시 I/O 오류가 밖으로 나감, 청소가 준비 중인 디렉터리를 삭제). 사람을 거치지 않고 재작업.
- step-003 v1→v2: Worker 실수. Gate G-006 fail — 코드와 AC 는 통과, store.md 에 옛 문장 3곳이 남음. 문장 하나를 고치면 그것을 가리키던 다른 문장이 틀려진다. 사람을 거치지 않고 재작업.
- Gate 오판은 없었다. 다만 G-001 은 결함 3건을 적고도 verdict 가 pass 였다 — "어떤 지적이 승인을 막는가" 가 G-002 부터 severity/class 로 드러나게 되었다(F11).

## 실행 중 개입
- 이벤트로 기록된 개입(세션에 보낸 메시지)은 없다. Worker 가 대화 세션이었으므로 사람의 말은 이벤트를 거치지 않고 바로 Worker 에게 갔다 — ADR-0006 의 경로는 시험되지 않았다.
- step-001 의 F-002 는 형식은 검토 피드백이지만 내용은 설계 방향의 지시다. "조용히 깨지는 것보다 시끄럽게 잠기는 쪽" 이라는 원칙은 Task 의 constraints 에 미리 있을 수 있었다.

## 반복 패턴 (Skill 후보)
- 설계 Step → 구현 Step → 호출자·문서 정합 Step 의 3단 구성. 한 번뿐이라 아직 Skill 로 뽑기엔 이르다.
- Reviewer 패킷: 작업 노트의 "확인하지 못한 것" 을 먼저 공격 + "값싸게 확인할 수 있으면 실행해서 확인". 실제 결함은 전부 여기서 나왔다. Skill 이 아니라 reviewer.md 의 기본 동작으로 넣는다.
- 문서 정합 검사: "고친 결과로 새로 틀려진 문장이 없는가".

## Context 부족 / 과잉
- **측정하지 못했다.** Worker 가 대화 세션이었으므로 Context 패킷만으로 작업할 수 있는지(roadmap 의 위험 2)는 알 수 없다. 사람은 Worker 도 별도 AI 에게 시킨 줄 알았고, 기록(Run 의 `session_path: new`)만으로는 구별되지 않았다.
- Ledger 만으로의 이어받기는 마무리 단계에서 한 번 성립했다: 새 세션이 `stage0-manual-operation.md`, ledger.md, events.jsonl 의 끝, G-007 만으로 D-004 를 쓰고 Task 를 닫았다. 부족했던 것 — 사람의 최종 확정을 어디에 기록하는지(Task 수준 Feedback 의 자리가 없다, F4), merge 방식(직접 merge vs PR)의 기본값. 구현 Step 을 이어받는 경우는 시험되지 않았다.
- 미확인으로 남은 것: POSIX 에서의 실행.

## 기록의 정확성
- 이벤트와 엔티티의 시각이 Task 생성 시각을 빼면 추정값이었고 뒤로 갈수록 실제보다 앞섰다(seq 104 는 15:45Z 로 적혔으나 실제 11:49Z). 마무리 세션이 발견했다. append-only 이므로 고치지 않았고 seq 105 부터 실제 시각을 적어 `at` 이 한 번 거꾸로 간다. 도구가 생기면 없어지는 문제지만, 수동 운영이 남아 있는 동안은 시각을 추정하지 않고 얻어서 적는다.
- 앞 단계가 실패했는데 commit·push 가 진행된 사고 2회, 한 줄에 여러 이벤트가 쓰인 events.jsonl 을 push 한 사고 1회. `append-events` / `validate-data` 스크립트와 "검증 뒤에만 commit" 규칙으로 막았다.
- 운영 스크립트를 세션 임시 폴더에 두었다가 잃은 적이 있다 → repo 의 `scripts/` 로.
