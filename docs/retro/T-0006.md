## Planner 제안과 사람의 결정

- Intake에서 사람은 Task 발행·done도 범위에 넣고 Ledger 자동 작성은 제외했다. Ledger를 사람이 쓰지 않게 만드는 방향은 정했지만 방법은 정하지 않았다. Orchestrator가 이를 '역할이 직접 쓴다'로 좁혔다가 사람의 지적으로 바로잡았다.
- step-001에서 사람은 역할 출력은 데이터 밖에서 받아 command가 blob으로 저장, deterministic 문서는 Gate와 함께 기록, Worker JSON 사용, 승인은 사람이 본 Gate를 지정하는 방식을 골랐다(F-001).
- step-002 승인 때 append-events의 ref 검사를 다음 Step에서 반드시 고치도록 했다(F-003). 스키마 자체의 pattern은 별도 범위로 남겼다.
- D-003의 Step 한 바퀴 분할을 사람이 받아들이지 않고 하나로 합치게 했다(F-005). R-008은 R-007을 resume해 D-004를 냈고 step-003은 미실행 cancelled다. proposed 직후 status 비교는 step.proposed를 기준으로 읽는 해석도 사람이 확정했다.
- 검토 시 사람은 '두 산출물이 무엇인가', '새 Worker가 어떤 코드에서 어떻게 재작업하는가'를 물었다. 이름·Gate 등급만으로 승인 대상을 이해시키지 못한다. 내용·시작 HEAD·실패 이유·전체 재검토를 먼저 설명해야 한다.

- 사람의 지시로 Codex가 직접 최대 1초의 제한된 재시도를 구현했다. 대상이 없고 EPERM·EBUSY·EACCES일 때만 재시도하며, 다른 키·비일시 오류·지속 오류는 거부한다. 경쟁자가 같은 키를 먼저 게시하면 기존 raced 경로로 읽는다. 회귀 6개를 더해 Task worktree와 main에서 594개 모두 통과했다. 파일을 잠근 외부 주체는 확인하지 못했으므로 보안 프로그램 탓이라고 단정하지 않는다. 구현 변경은 구조 경계·기존 ADR을 바꾸지 않았다.

## 실행 방식·Orchestrator 교체

- 역할 실행은 R-001·002 서브에이전트 → R-003~005 빈 폴더의 claude -p → R-006부터 Task worktree의 claude -p로 바뀌었다. Codex Orchestrator 인계 뒤 Reviewer R-010·012·015·017은 별도 Codex CLI gpt-6-astra였다.
- 인계 기록·원문 패킷·실행 JSON이 있어 Claude Code에서 Codex로 기록을 이어받았다. 앞 세션은 더 쓰지 않는다는 확인과 실행 직전 HEAD 비교를 했다. 모델·cwd·세션 id는 실제 실행 기록과 대조했다.
- 분리된 감독 프로세스, stdout·stderr 파일, 제한 시간, completion 파일과 heartbeat로 대화 턴이 끝나도 이어갔다. submitted 이벤트만 보고 실패로 분류하는 옛 절차는 detached 프로세스를 중복 실행할 수 있어 수정했다. JSON stdout이 끝까지 비어 있을 수 있다는 점도 기록했다.
- R-008 resume은 168초·6턴·목록가 3.57 USD였다. 새 R-007은 233초·19턴·2.50 USD였다. 시간·턴이 줄었다고 비용도 줄어드는 것은 아니다(표본 하나). resume 일반 정책은 구현 때 논의하기로 했다.
- 작업 폴더를 비워도 계정 커넥터가 들어왔고, worktree에서는 프로젝트 지침과 메모리 기능 안내가 들어왔다. 격리는 cwd만으로 해결되지 않는다. CLI 세션 로그와 Run 연결, 출력 디렉터리 수명, 권한 설정은 Runner 설계 과제다.
- Reviewer 임시 실험 폴더 4개(R-010·012·015·017)의 삭제는 자동 승인 검토에서 blocked by policy로 거부됐다. 추가 사유는 없었고 우회하지 않았다. Task/data worktree 19개는 깨끗함과 절대 경로를 확인해 제거했다. 기준 SHA 기록용 checkout은 마지막 기록 뒤 제거한다.

## Context·운영에서 드러난 것

- Ledger로 다음 판단의 틀은 섰고 세부 증거에는 원본 Task·Gate·Feedback·테스트가 필요했다(R-018 packet_gaps). Ledger는 근거를 대체하지 않는다. 완료 시 S1~S7 원문 대조가 한계를 사람에게 드러내는 역할을 했다.
- 'merge 전 새 ADR도 기존 ADR인가'가 재작업에서 모호했다. Orchestrator는 수정 금지를 보수적으로 적용했고 문구 의견이 남았다. ADR 작성 시점과 교정 규칙은 여전히 정해야 한다.
- 새 command는 역할 출력과 packet_gaps를 받아들이지만 종료 후 backend_session_id·실제 종료 시각·CLI 로그를 전용 입력으로 붙이는 길은 없다. Ledger·운영 로그만으로 이어지는 한계가 새 운영 절차에 명시됐다.
- 수동 기록은 끝까지 baseline 18fb89e였다. main merge 뒤 baseline checkout을 별도로 만들어 옛 스크립트를 계속 사용했다. 운영 문서는 merge 직후 새 입구·출력 위치·Ledger 분리 규칙에 맞췄다.
- Orchestrator의 문서 교체 패치가 같은 경로에 delete/add를 한 요청에 넣어 거부됐다(파일 변경 없음). 직접 보완 테스트 초안에는 PathLike/문자열 타입 오류가 있었고 typecheck에서 잡혀 commit 전에 고쳤다. 검증 실패 뒤 commit하지 않는 규칙을 지켰다.

## 반복 패턴과 단계 전환 판단

- 실패 Gate 전체·원래 정의·이전 commit·노트를 새 Worker에게 주고 추가 commit을 만든 뒤 새 Reviewer가 전체 버전을 보는 패턴이 두 번 성립했다.
- 입구만 사용하는 전체 흐름 검사, 거부 시 파일 내용 불변, 최신 데이터 고정 사본의 새/옛 validator 비교는 운영 명령 변경의 재사용 가능한 검증 패턴이다. 아직 Skill로 추출하지 않는다.
- Task 수 기준은 6개로 충족한다. 이번 Task는 스키마를 범위에서 제외했으므로 '변경이 없었다'만으로 안정화를 선언할 수 없다. stored_in·참조 pattern·Feedback 전달·Gate 판정·실행 메타데이터의 빈자리가 남았다. **0→1단계 전환은 미확정**이며 Workspace 최소 기능을 다음 후보로 권하되, 사람이 다음 Intake에서 고른다.
