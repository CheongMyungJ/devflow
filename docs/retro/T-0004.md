2. **기존 항목과의 중복.** backlog 에 같은 뿌리의 항목이 이미 있는지 읽어야 했다(하위 세션의 기록, 'JSON 파일' 문장, ADR 의 기준). 새로 쓰면 같은 문제가 두 곳에서 따로 자란다. "또 나왔다(몇 번째)" 를 덧붙이는 쪽이 우선순위 판단에 쓸모 있다.
3. **한 후보를 나누거나 여럿을 합치기.** G-002 의 한 줄은 "고칠 문장 넷" 과 "실측되지 않은 경로" 로 성격이 달라 나눴고, packet_gaps 에서 온 자잘한 것들은 뿌리가 같은 것끼리 합쳤다.
4. **어디에 둘 것인가.** 2번(지금 고칠 수 있는 스키마·지침)인가 4번(Orchestrator·Runner 를 만들 때 정할 것)인가. 설정 파일은 Runner 가 생겨야 뜻이 있어 4번에, intake.md 다듬기는 2번에.
5. **결정과 의견을 구별해 적기.** 사람의 질문에 대한 Orchestrator 세션의 답은 결정이 아니다 — "사람의 말" 과 "의견(결정된 것이 아니다)" 을 나눠 적었다. 설정 파일 항목은 사람의 요청(무엇을 원하는가)을 앞에, 의견을 "정할 것 (1)~(5)" 로 뒤에.
6. **"지금 고치지 말고 다시 보이는지 본다" 를 함께 옮기기.** F-004 의 결정은 "backlog 로" 만이 아니라 "표본이 하나다" 라는 이유가 붙어 있다. 이유 없이 옮기면 다음 세션이 바로 고치려 든다.
7. **다음 권고를 다시 쓸 것인가.** backlog 의 머리말("다음 권고는 …")이 끝난 Task 를 가리키고 있었다. 새 권고는 의견으로 표시해 적었다 — 순서는 사람이 정한다.

→ "후속 조치가 남는 자리"(backlog 4번)의 판단 재료: 나가는 쪽을 시스템이 기계적으로 모으더라도(Gate 의 B, "확인하지 못한 것", packet_gaps) 위의 1~3 은 누군가의 판단이다. 출처의 참조(Gate id, Run id)가 후보마다 붙어 있었던 것이 1번을 가능하게 했다.
