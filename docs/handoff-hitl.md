# 다음 세션용 프롬프트: 역할별 HITL과 독립 질문 CLI

아래 내용을 다음 개발 세션의 작업 요청으로 사용한다. 이 문서는 후속 작업의 합의와 인계 자료이며 현재 구현된 계약이나 엔티티 필드 정의가 아니다.

devflow의 R01·R02 실행 기반 위에 **이해하기 쉬운 역할별 HITL과 독립 질문 CLI**를 구현해줘. 설명이나 설계안만 제시하고 끝내지 말고 코드·테스트·문서까지 진행해줘.

먼저 `AGENTS.md`, `docs/roadmap.md`, `docs/architecture.md`, `docs/design/commands.md`, `docs/design/runner.md`, 관련 ADR과 실제 코드를 읽어라. 시작 기준은 main `21ec52f`에서 만든 `codex/role-settings-and-execution` 브랜치다. Git과 PR에서 최신 반영 상태를 확인하고, 병합됐다면 최신 main, 미병합이면 해당 PR head를 기반으로 `codex/` 작업 브랜치를 만들어라. 사용자 변경은 보존한다.

## 이미 구현된 것과 이번 목표

현재 역할별 backend/model/reasoning 설정, 새 세션 Planner·Worker·Reviewer 실행, 2단계 Intake, 상태·수집·취소·로그·일부 backend의 실행 중 메시지 전달이 있다. 역할 실행과 결과 기록까지 구현됐고, 역할별 HITL·승인 후 자동 조율·독립 질문 CLI·deterministic Gate 실행·전체 `advance` 루프는 아직 없다. baseline 검증은 Windows / Node 22.15.1에서 타입 검사와 49개 파일 707개 테스트 통과, 마지막 Intake 버전 검사 변경 후 관련 4개 테스트 추가 통과다. Codex와 Claude Code는 각각 Worker → 독립 Reviewer 실제 연동을 확인했고, OpenCode 실제 모델 연동은 미검증이다.

사용자가 원하는 기본 선택은 **승인 / 수정 요청**, 보조 선택은 **질문 CLI 열기**다. 복잡한 대화 분류나 새 채팅 플랫폼 없이 이 흐름이 실제로 이어지게 구현한다. HITL은 설정에 따라 Planner·Worker·Reviewer 각각의 결과 직후에 둘 수 있다. Planner 결과를 사람이 보려는데 Reviewer부터 실행하는 식으로 단계를 합치지 않는다.

## 역할별 흐름

- **Planner:** 결과 → 해당 HITL. 승인은 해당 제안을 확정하고 다음 동작으로 진행한다. 수정 요청은 기존 제안과 사람의 요구를 전달해 새 Planner 세션에서 재제안하고 다시 Planner HITL로 돌아온다. 과거 제안을 덮어쓰지 않는다.
- **Worker:** 결과 → 해당 HITL. 승인은 선언된 검증으로 진행한다는 의미이며 최종 Artifact 승인을 대신하지 않는다. 수정 요청은 같은 Task worktree에서 새 Worker 세션으로 처리하고 새 Artifact 버전을 만든 뒤 다시 Worker HITL로 돌아온다. 검증은 Step의 deterministic/semantic 계약을 따른다.
- **Reviewer:** 결과 → 해당 HITL. 승인은 검토 판정을 수용한다는 뜻이다. pass는 다음 진행, fail은 재작업 경로이며 실패 결과를 통과로 바꾸지 않는다. 수정 요청은 코드·산출물 변경이면 Worker, 검토 판단 재검토이면 새 Reviewer로 분기한다. 필요할 때만 간단한 대상 선택을 제공한다. 재검토도 정확한 Artifact 버전을 대상으로 하고 이전 Gate 기록은 보존한다.

모든 승인·수정 요청은 현재 대기 중인 결과를 정확히 지목하고, 중복 입력·오래된 결과 승인·다음 단계 진행 후 과거 결과 수정이 현재 상태를 잘못 바꾸지 않도록 한다. 재작업 결과는 활성화된 해당 HITL로 다시 돌아온다. 질문 답변이나 CLI 종료를 승인으로 해석하지 않는다.

## 독립 질문 CLI의 책임 범위

1. devflow에서 초기 질문을 입력하면 현재 역할과 결과, 승인 대상 버전, 관련 작업 노트·Gate·Feedback 등 질문 시점의 Context를 새 질문용 대화형 CLI에 전달한다. 사람이 그 창에서 자유롭게 질의응답한다. 기존 역할 세션 resume는 필요 없다.
2. **devflow는 CLI 실행 인계 후 즉시 복귀한다.** 종료 대기, 대화 추적, 답변 수집·요약·동기화는 하지 않는다. 창이 열린 동안에도 사용자는 devflow에서 승인·수정 요청하고 다음 단계로 진행할 수 있다.
3. 질문 CLI를 Task의 관리형 Run이나 진행 잠금으로 등록하지 않는다. 실행 인계 실패는 사용자에게 알려주되 Task 실패로 바꾸지 않는다. 인계 이후 CLI 내부의 인증·모델 오류나 종료도 본 작업 상태에 반영하지 않는다.
4. 질문 환경은 읽기 전용이어야 한다. ‘수정하지 말라’는 프롬프트만으로 보장했다고 하지 말고 backend의 권한 제한과 격리된 읽기 자료를 사용한다. Task worktree·Artifact·State Store를 변경할 수 없어야 한다. 실제 수정은 devflow의 수정 요청으로만 반영한다. 지원 여부를 확인하지 못한 backend는 명확하게 미지원 처리한다.
5. 화면과 초기 Context에 **질문 시점의 결과 기준**임을 표시한다. 문서는 정확한 버전의 내용, 코드는 고정 SHA 등으로 제공한다. 진행 중 worktree의 최신 내용을 읽으면서 과거 결과의 스냅샷이라고 주장하지 않는다. 기록되지 않은 원래 세션의 사고 과정까지 알 수 있다고 설명하지 않는다.
6. AI 실행은 여전히 Runner 인터페이스를 통한다. 질문용 실행 인계 계약을 관리형 작업 실행과 구별하고, backend CLI 옵션과 터미널 실행 세부 사항은 어댑터 안에 둔다. 지원 환경에서 실제 대화형 창을 여는 데 필요한 최소 구현을 한다.
7. 초기 질문·대상 참조·실행 인계 시도/결과의 최소 기록은 가능하지만 이후 사람이 native CLI에서 주고받는 모든 메시지를 기록하겠다고 약속하지 않는다. 기존 AGENTS 9번/ADR-0006의 메시지 선기록 규칙과 충돌하므로 새 ADR을 작성하고, AGENTS의 적용 범위를 이 독립 질문 통로에 한정해 명확히 조정한다. 관리형 역할 세션 메시지의 기존 규칙은 유지한다. 기존 ADR 본문은 다시 쓰지 않는다.

## 우선 확인할 현재 코드의 제약

- `src/commands/plan.ts`: 열린 Step이 있으면 다음 Step 제안을 거부하므로 Planner 재제안의 기존 제안 보존·대체 관계가 필요하다.
- `src/commands/transitions.ts`: Worker 완료 뒤 checking으로 가지만 기존 수정 요청은 in_review 기준이다. Gate 전 Worker HITL과 재작업 경로가 필요하다.
- `src/commands/roles.ts`, `src/commands/gates.ts`: Reviewer 실행 가능 상태와 Gate 기록 시 상태 전이가 정해져 있다. Reviewer HITL 대기와 같은 버전 재검토를 지원하되 판정 기록과 진행 결정을 구별해야 한다.
- `src/commands/execution.ts`, `src/queries/execution.ts`, `scripts/execution.mjs`: 현재 실행 제어 입구에 HITL 조회·승인·수정 요청·질문 CLI 열기를 연결한다. 기존 실행 중 메시지 API를 완료 후 질문 통로로 재사용하지 않는다.
- Context에 원래 Planner 제안, 수정 요청, 승인 기준, 재작업 이력이 충분히 전달되는지 점검한다. 새 세션이 앞 대화를 암묵적으로 기억한다고 가정하지 않는다.
- 관리형 Run의 수집 완료만으로 HITL 대기가 표현되지 않는다. 영속적인 대기 대상과 중복 처리 규칙을 설계한다. 승인 후 이어지는 최소 Orchestrator와 필요한 Gate 실행까지 연결해야 사용자 흐름이 완성된다. 버튼 추가만으로 완료했다고 하지 않는다.

이 목록은 조사 시작점이며 실제 코드로 다시 확인해라. 정확한 엔티티 필드는 schema에서 정의하고 생성 타입을 사용한다. CLI는 commands/queries만 호출하고 State Store의 파일 구현을 참조하지 않는다. 공유 상태에 로컬 경로를 저장하지 않는다. append-only 이벤트, 버전별 승인, 단일 Task worktree, 멱등 advance, 종료 불명확한 실행의 자동 대체 금지 규칙을 지킨다.

## 범위와 완료 기준

resume, 기존 Worker native CLI 인계, 자체 채팅 UI, AI로 사용자 의도를 분류하는 조율기, 답변 자동 반영, 범용 세션 관리 플랫폼은 이번 범위에서 제외한다. 구조 변경 이유는 새 ADR에, 현재 구조와 사용법·남은 한계는 기존 문서에 반영한다. ADR-0021의 ‘승인 / 세션 접속, 접속 종료까지 대기’는 이전 후속 제안이며 이번 사용자 합의가 우선한다.

역할별 승인·재작업·재검토, 중복/오래된 승인, 실패 판정의 처리, 재작업 후 새 버전 검증을 의미 있는 테스트로 확인한다. 질문 창이 계속 열려 있어도 본 흐름이 진행되고, 질문 실행이 관리형 Run 잠금을 만들지 않으며, 실행 인계 실패가 Task를 실패시키지 않는지 확인한다. 질문 자료의 버전 고정과 쓰기 제한도 검사한다. CLI 계약 테스트와 실제 실행 검증을 구분하고 OpenCode 실제 연동을 근거 없이 완료 처리하지 않는다.

`npm run typecheck`, `npm test`를 실행하고 실제 구현된 사용자 흐름과 남은 제한을 보고해라. 일반적인 구현 선택은 자율적으로 진행하고 사용자의 반복 승인을 요구하지 않는다. 이 요청만으로 merge·배포는 하지 않는다.
