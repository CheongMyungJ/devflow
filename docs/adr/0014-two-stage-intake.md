# ADR-0014: Intake 는 두 단계 — 의도 확인 뒤에 정의 확인

- 상태: Accepted
- 날짜: 2026-09-19

## 상황
Intake 는 질문 몇 개 뒤에 완성된 Task 정의(AC 여러 개, 긴 background)를 통째로 보여 주고 확인받았다. 사람이 한 번에 읽어야 할 양이 많고, 무엇이 어긋났는지 찾기 어렵다(T-0003 의 Intake 에서 사람이 "좀더 쉽게 설명해줘" 라고 했다). Planner 는 AC 만 보고 done 을 판단하므로 의도와 AC 가 어긋나면 잘못된 곳에서 done 이 난다.
ADR-0013 이 그 의도를 담을 칸(problem, success_criteria, affected, non_goals, open_questions, covers)을 Task 양식에 만들었다. 이 ADR 은 그 칸을 채우는 **절차**를 정한다. 칸의 뜻은 `schemas/task.schema.json` 의 description 이 기준이고 여기서 다시 쓰지 않는다.

## 결정
1. **Intake 는 두 단계다.** 1단계 "의도 확인" — 7칸(문제 / 바라는 결과 / 식별 가능한 성공 기준 / 영향받는 사람과 시스템 / 제약 / 범위 밖 / 열린 질문)의 짧고 쉬운 말의 초안을 사람에게 리뷰받는다. 이 초안에는 AC 를 쓰지 않는다. 2단계 "정의 확인" — 1단계가 맞은 뒤에만 AC 와 범위를 쓰고, 사람이 볼 것을 "이 AC 들이 그 의도와 성공 기준을 제대로 검사하는가" 로 좁혀 확인받은 뒤 발행한다.
2. **사람 확인 지점은 둘이다.** 의도 초안의 확인이 첫 승인 지점이고, 발행 전 정의 확인이 둘째다(`docs/architecture.md` 7절).
3. **열린 질문의 담당자는 1단계에서 정한다.** 셋 중 하나다 — 사람이 Intake 중에 답함 / Planner·Worker 에게 맡김 / 조사 Step 으로 확인. 앞의 것은 의도 초안에만 존재하는 상태다: 답을 받아 해당 칸에 옮겨 적고 질문을 지운다.
4. **발행 차단은 양식과 지침이 함께 지킨다.** 양식은 사람을 뜻하는 담당자 값을 두지 않아 그런 Task 를 거부하고(ADR-0013 결정 4), 지침은 발행 전에 남은 질문을 직접 되짚고 사람이 답할 질문을 다른 칸에 문장으로 숨기지 않게 한다. 스키마가 볼 수 없는 것(id 의 존재와 중복, 모든 성공 기준이 AC 로 옮겨졌는가, `success_criteria` 가 비어 있지 않은가)도 발행 전 되짚기에 둔다.
5. **업무 유형별 비중(조사·연구형, 버그·장애, 유지보수, 끝이 없는 일은 Task 가 아니다)은 `roles/intake.md` 에만 둔다.** 스키마에 유형별 구조를 만들지 않는다.

## 이유
- 1, 2: 어긋남은 짧은 글에서 가장 싸게 드러난다. 의도가 확정된 뒤에 AC 를 보면 사람이 볼 질문이 "이게 내가 원하는 것인가" 와 "이 검사가 그것을 잡는가" 로 나뉜다 — 한 번에 둘 다 보는 것보다 각각이 정확해진다.
- 3: 담당자를 붙이지 않으면 열린 질문은 미뤄둔 결정이 쌓이는 칸이 된다. 누가 답하는지가 정해져야 뒤의 역할이 "스스로 정해도 되는가" 를 안다.
- 4: 스키마의 거부는 정직하게 적힌 값에만 걸리고, 그 오류 문장은 오타의 거부와 구별되지 않는다(T-0004 에서 양식을 만든 Step 의 검토에서 나온 지적). 지침만으로도, 양식만으로도 성립하지 않는다.
- 5: 유형이 바꾸는 것은 칸이 아니라 어느 칸이 두꺼워지는가다. 스키마에 넣으면 유형별 분기가 생겨 옛 기록과 새 기록을 가르는 장치가 늘어난다.

## 포기한 대안
- 지금처럼 한 번에 확인하고 초안은 Intake 안에서만 쓰기: 사람이 확인한 말이 Task 에 남지 않아 Task 를 끝낼 때 원문과 대조할 수 없다(ADR-0013 결정 1 이 그 칸을 만든 이유와 같다).
- 사람이 답할 질문을 Task 에 남기고 뒤에서 묻게 하기: 발행된 Task 는 사람 없는 세션들이 읽는다. 물을 자리가 `ask_human` 뿐인데 그때는 이미 Step 이 돌고 있다.
- 두 단계를 스키마(예: 초안 엔티티)로 강제하기: 1단계의 산출물은 대화 중의 초안이고 저장되는 것은 Task 하나다. 엔티티를 늘리면 발행 전의 상태를 저장·복구해야 한다.
- 업무 유형별로 필수 칸을 다르게 하기: `type` 이 바뀌면 이미 발행된 Task 의 검사가 바뀐다.
