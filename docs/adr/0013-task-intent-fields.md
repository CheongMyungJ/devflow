# ADR-0013: Task 정의에 의도의 칸, AC 는 성공 기준을 가리킨다, 사람이 답할 질문이 남으면 발행되지 않는다

- 상태: Accepted
- 날짜: 2026-09-19

## 상황
Planner 는 AC 만 보고 done 을 판단하므로 사람의 의도와 AC 가 어긋나면 잘못된 곳에서 done 이 난다. 그런데 Task 양식에는 의도를 담을 칸이 goal 뿐이었다. T-0002, T-0003 은 "범위 밖" 과 "일부러 정하지 않은 것" 을 constraints 에 문장으로 끼워 넣었고, 문제는 background 에 배경 사실과 섞였다. 뒤의 역할은 "일부러 정하지 않은 것" 과 "깜빡한 것" 을 구별할 수 없었다. 사람의 결정(T-0004 의 Intake)으로 Intake 는 의도 초안을 먼저 확인받고 그 뒤에 AC 를 쓴다 — 그 초안의 내용이 Task 정의에 남아야 한다.

## 결정
1. **Task 에 의도의 칸 다섯을 둔다**: `problem`(문장), `success_criteria`(`{id: S<n>, text}` 의 배열), `affected`, `non_goals`(문장의 배열), `open_questions`(`{id: Q<n>, text, answered_by}` 의 배열). 바라는 결과는 `goal`, 제약은 `constraints` 그대로다. 칸의 뜻과 기존 칸과의 구별은 스키마의 description 이 기준이다.
2. **다섯 칸은 선택 필드다.** 필드가 없으면 "옛 양식의 기록이거나 적지 않았다", 빈 배열은 "없다고 확인했다" 다(ADR-0012 결정 4 의 적용 — 옛 기록은 고치지 않고, 허용은 Task ID 가 아니라 형식에 둔다). 새 Task 가 칸을 채우게 하는 것은 Intake 의 역할 지침이 맡는다.
3. **AC 가 성공 기준을 가리킨다**: `acceptance_criteria[].covers` 에 성공 기준의 id 들. 빈 배열은 "어느 성공 기준도 옮긴 것이 아니다"(전체의 바닥 같은 AC), 필드가 없으면 대응을 적지 않은 것이다.
4. **사람이 답해야 할 열린 질문은 발행된 Task 에 있을 수 없다.** `answered_by` 의 값은 `planner_or_worker` 와 `investigation_step` 둘뿐이고 사람을 뜻하는 값이 없다 — 그런 값을 쓴 Task 정의는 Task 스키마가 거부하므로 발행(createTask → Store 의 스키마 검증)도 거부된다.

## 이유
- 1: 끼워 넣은 문장은 관례에 기대고, 관례를 모르는 새 세션은 칸이 없으면 묻지도 적지도 않는다(T-0003 의 "이 Task 자신의 기록도 다시 검사된다" 는 Intake 가 놓쳤다). 성공 기준은 사람이 확인한 말 그대로 남아야 Task 를 끝낼 때 AC(AI 가 옮긴 번역본)가 아닌 원문과 대조할 수 있다.
- 2: 옛 기록 넷에는 이 칸이 없고 고칠 수 없다. 필수로 하려면 옛 양식과 새 양식을 가르는 장치(버전, 합집합)가 필요한데 선택 필드의 검사는 칸을 쓴 순간 똑같이 엄격하므로 그 장치가 주는 것이 없다.
- 3: AC 는 실행 중에 늘어난다(`added_by`). 대응을 AC 쪽에 두면 AC 를 더할 때 성공 기준을 고치지 않아도 된다. "옮긴 것" 이라는 관계의 방향과도 같다.
- 4: 발행은 Store 의 스키마 검증만 거친다 — 지침이나 사후 검사(validate-data)에만 두면 발행은 된다. 값을 두지 않는 방법은 조건 키워드(not, if/then, contains)가 필요 없어 생성 타입이 구체적인 유니온으로 나오고(T-0003 에서 타입 없는 anyOf 가지가 생성 타입을 두 번 뭉갰다), 타입에서도 막힌다.

## 포기한 대안
- `answered_by` 에 `human` 을 두고 `not`/`contains` 로 거부: 생성 타입이 `human` 을 받아 타입과 스키마가 어긋나고, 오류 메시지("must NOT be valid")가 이유를 말하지 않는다. 얻는 것은 "아는 값인데 남아 있어 거부" 와 "모르는 값" 의 구별뿐이다.
- 성공 기준 쪽에 AC 목록을 두거나 별도의 대응표를 두기: AC 가 늘 때 두 곳을 고쳐야 하고, 대응 없는 AC 를 표현하려면 또 다른 표시가 필요하다.
- 성공 기준과 AC 를 한 칸으로: 사람이 확인한 말과 검증 가능한 문장은 독자와 쓰임이 다르다. 합치면 지금처럼 AC 만 남는다.
- `covers` 가 가리킨 id 의 존재를 검사하기: JSON Schema 로는 표현할 수 없고 validate-data 에 두면 발행을 막지 못한다. 한계로 description 에 적었다.
- `affected` 를 `{kind: person | system, …}` 의 객체로: 구별을 쓰는 곳이 아직 없다.
