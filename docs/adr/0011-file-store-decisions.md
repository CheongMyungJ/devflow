# ADR-0011: Store 파일 구현체의 결정

- 상태: Accepted
- 날짜: 2026-09-18
- ADR-0008 의 결정 4 중 "Task ID 발급을 파일 lock 으로 직렬화한다" 를 대체한다. 같은 결정의 `devflow-data` commit 직렬화 부분은 그대로다.

## 상황
T-0001 에서 State Store 의 인터페이스와 파일 구현체를 만들었다. 설계는 세 번, 구현은 한 번 고쳐졌고 그 과정에서 기존 문서와 다른 결정이 내려졌다. 상세는 `docs/design/store.md`, 호출자 규약은 `docs/design/commands.md`.

## 결정
1. **Task ID 는 전역 lock 없이 발급한다.** 다음 번호의 Task 디렉터리를 `mkdir` 하고 이미 있으면 다음 번호로 넘어간다. ID 는 유일하지만 연속은 아니다.
2. **살아 있는 프로세스의 lock 은 절대 빼앗지 않는다.** Task 별 lock 은 같은 호스트·플랫폼에서 소유자의 pid 가 죽은 경우에만, 회수 전용 lock 아래에서 회수한다. 시간 기준 회수는 하지 않는다. pid 재사용이나 회수 도중의 crash 로 lock 이 남으면 `StoreBusyError` 가 무엇을 지우면 되는지 안내하고, 사람이 푼다.
3. **"이벤트는 append-only" 는 성립한 commit 의 이벤트에 대한 규칙이다.** commit 도중 죽어 성립하지 못한 commit 의 잔여물을 복구가 잘라내는 것은 위반이 아니다. 복구는 메모해 둔 내용과 바이트 단위로 일치하는 것만 자르고, 예상 밖의 상태는 건드리지 않고 오류로 멈춘다.
4. **파일 시각을 판정에 쓰지 않는다.** lock 의 stale 판정에도, 읽기의 일관성 표식에도 쓰지 않는다.
5. **한 호스트, 한 플랫폼.** 여러 호스트나 Windows·WSL 이 같은 데이터 디렉터리를 함께 쓰는 것은 지원하지 않는다. 전원 장애에 대한 내구성은 보장하지 않는다(프로세스 crash 에 대한 원자성만).
6. **프로세스마다, 데이터 위치마다 Store 인스턴스는 하나.**

## 이유
- 1: `mkdir` 의 원자성만으로 유일성이 보장된다. lock 이 하나 줄면 죽은 소유자 처리도 하나 준다.
- 2: 판단이 틀릴 때 "기록이 조용히 깨지는" 쪽이 아니라 "Task 가 시끄럽게 잠기는" 쪽으로 틀리게 한다. 시간 기준 회수는 멈췄다 깨어난 소유자가 새 소유자의 상태를 망가뜨리는 경로를 만들었고, 막으려 할수록 메커니즘이 늘었다.
- 4: 실측에서 NTFS 의 mtime 이 같은 tick 안의 변경을 구별하지 못했다(append 후 잘라내기가 원래와 같은 크기·mtime 을 남긴 경우가 2000회 중 863회). 시계 점프(절전 복귀, 시간 동기화)도 시간 기준 판정을 깨뜨린다.
- 5, 6: 파일 구현체는 DB 구현체로 교체될 부품이다(roadmap 4단계). 정교하게 만들기보다 가정을 좁히고, 가정이 깨지면 드러나게 한다. 이 제약들은 Store 인터페이스에 나타나지 않는다.

## 포기한 대안
- 시간 기준 stale 판정 + 소유자의 자진 포기(설계 v2): 확인 지점 밖의 모든 파괴적 동작이 빈틈이 되었다.
- mtime heartbeat 기반의 lock 라이브러리: 결국 시간 기준이다.
- OS 의 배타적 파일 열기: 프로세스가 죽으면 OS 가 풀어 줘 가장 깔끔하지만 Node 가 share mode 를 노출하지 않아 native 의존성이 필요하다.
- 완전한 event sourcing: 이벤트마다 엔티티 전체를 실어야 하고, 사람이 `task.yaml` 을 바로 읽는 이점이 사라진다.
